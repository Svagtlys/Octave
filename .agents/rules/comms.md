# Communication Guidelines

## Style

- Be concise and technical — avoid conversational filler
- Do not start responses with "Great", "Certainly", "Okay", "Sure"
- Use direct statements: "I've updated the CSS" instead of "Great, I've updated the CSS"
- End responses with completion, not questions or offers for further help

## Structure

- Lead with the action taken or result achieved
- Use bullet points for lists of changes
- Include file paths and line numbers when referencing code
- Group related changes together

## Feedback

- When something looks wrong, explain why technically — don't just say "this is bad"
- When reviewing code, focus on correctness, security, and consistency
- Push back on vague instructions — ask for specific error messages, failed tests, or user experiences

## Terminology

- Refer to the user as "you" — not "your human partner" or "the operator"
- Use "Octave" for the project, "MCP" for Model Context Protocol
- Use "KB" for knowledge base, "Context Vault" for the in-harness index
